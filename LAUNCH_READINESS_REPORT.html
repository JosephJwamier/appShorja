▲ أولًا: عوائق Google Play الحرجة

A1 معرّف الحزمة لا يزال com.example.marketplace_app رفض مؤكد

الدليل
android/app/build.gradle.kts → namespace وapplicationId
الأثر
Google Play يرفض صراحةً أي تطبيق معرّفه يبدأ بـ com.example. والأخطر: لا يمكن تغيير applicationId إطلاقًا بعد أول رفع — سيبقى هوية التطبيق للأبد.
الحل: اختر نطاقًا عكسيًا حقيقيًا (مثال com.eshorja.app) وغيّره في: namespace + applicationId (Android)، ومجلد كود Kotlin، وiOS Bundle ID، ثم أعد إنشاء ملفات Firebase على المعرّف الجديد.
// android/app/build.gradle.kts
android {
    namespace = "com.eshorja.app"
    defaultConfig { applicationId = "com.eshorja.app" }
}

A2 بناء الإصدار موقّع بمفتاح debug رفض مؤكد

الدليل
build.gradle.kts: release { signingConfig = signingConfigs.getByName("debug") } — ولا يوجد key.properties ولا keystore.
الأثر
Play Console يرفض حزمة AAB موقّعة بمفتاح التطوير. مطلوب مفتاح رفع (upload key) حقيقي.
الحل: أنشئ keystore، اربطه عبر key.properties (غير مُتتبَّع في git)، وفعّل Play App Signing.
# 1) أنشئ مفتاح الرفع
keytool -genkey -v -keystore ~/upload-keystore.jks -keyalg RSA \
        -keysize 2048 -validity 10000 -alias upload

# 2) android/key.properties  (أضِفه إلى .gitignore)
storePassword=****  keyPassword=****
keyAlias=upload      storeFile=/abs/path/upload-keystore.jks
// build.gradle.kts — اقرأ الملف وأنشئ توقيع release
val kp = Properties().apply {
    val f = rootProject.file("key.properties"); if (f.exists()) load(f.inputStream())
}
signingConfigs { create("release") {
    storeFile = file(kp["storeFile"] as String); storePassword = kp["storePassword"] as String
    keyAlias = kp["keyAlias"] as String;         keyPassword  = kp["keyPassword"] as String
}}
buildTypes { release {
    signingConfig = signingConfigs.getByName("release")
    isMinifyEnabled = true; isShrinkResources = true
}}

A3 أيقونة التطبيق = أيقونة Flutter الافتراضية جودة / رفض iOS

الدليل
res/mipmap-*/ic_launcher.png بأحجام 442–1443 بايت = أيقونة Flutter الزرقاء الافتراضية، ولا توجد إعدادات flutter_launcher_icons.
الأثر
Google Play يقبلها لكنها تُصنّف «تطبيق غير مكتمل/منخفض الجودة». وApple يرفض صراحةً الأيقونة الافتراضية (إرشاد 2.3.8 / 4.0).
الحل: صمّم أيقونة 1024×1024 (بدون شفافية لـ iOS) وولّد كل المقاسات آليًا.
# pubspec.yaml
dev_dependencies:
  flutter_launcher_icons: ^0.14.1
flutter_launcher_icons:
  android: true
  ios: true
  image_path: "assets/icon/app_icon.png"
  adaptive_icon_background: "#FFFFFF"
  adaptive_icon_foreground: "assets/icon/foreground.png"
# ثم: dart run flutter_launcher_icons

A4 استهداف إصدار أندرويد (targetSdk) وضغط الحزمة تحقّق مطلوب

الدليل
targetSdk = flutter.targetSdkVersion (يتبع إصدار Flutter المثبّت).
الأثر
Google Play يفرض على التطبيقات الجديدة استهداف Android حديث (API 35 حاليًا). تأكّد أن نسخة Flutter لديك توفّره، وإلا ثبّته صراحةً. فعّل أيضًا R8/تصغير الموارد لتقليل حجم AAB.

A5 روابط التطبيق (App Links) بدومين وهمي ميزة معطّلة

الدليل
AndroidManifest.xml → host="REPLACE_WITH_YOUR_DOMAIN.example"، وdeep_link_config.dart → kWebDomain = "https://REPLACE_WITH_YOUR_DOMAIN.example".
الأثر
روابط المشاركة (منتج/متجر/مزاد/بث) لن تفتح التطبيق. غير مانع للنشر لكنه يكسر ميزة أساسية. يتطلب نشر /.well-known/assetlinks.json ببصمة SHA-256 لمفتاح التوقيع.

◈ ثالثًا: التكامل مع الخادم (يكسر التطبيق في الإنتاج)

C1 عنوان API الافتراضي = محاكي أندرويد عبر HTTP لا يعمل في الإنتاج

الدليل
lib/config/api_config.dart: API_HOST الافتراضي = 10.0.2.2:8000 وAPI_SCHEME = http.
الأثر
10.0.2.2 هو عنوان حلقة المحاكي فقط — على هاتف حقيقي لا يوجد خادم هناك. وiOS يمنع HTTP (ATS). إن بنيت بلا --dart-define فالتطبيق المنشور «ميت» لا يتصل بأي خادم.
الحل: ابنِ دائمًا بتمرير الدومين الحقيقي وHTTPS (يُفضّل عبر سكربت بناء ثابت حتى لا يُنسى):
flutter build appbundle --release \
  --dart-define=API_HOST=api.eshorja.com \
  --dart-define=API_SCHEME=https

C2 لا يوجد دومين ولا خادم إنتاج بـ HTTPS شرط تشغيل

الأثر
التطبيق كلّه (تسجيل، منتجات، دردشة WebSocket، مزادات، بث، محفظة) يعتمد على الخادم. بدون دومين + استضافة + شهادة TLS لا يعمل شيء في الإنتاج، وتنكسر أيضًا App Links وUniversal Links.
الحل — الحد الأدنى للبنية:
  • دومين (مثل eshorja.com) + شهادة TLS (Let’s Encrypt) خلف Nginx.
  • خادم ASGI (Daphne/Uvicorn) — ضروري للـ WebSocket (channels)، وليس Gunicorn وحده.
  • MySQL + Redis + عامل Celery + Celery beat (تُشغّل مهام مجدولة: انتهاء الحجوزات/المزادات).
  • تخزين ملفات الوسائط (صور المنتجات) على تخزين دائم/سحابي، لا على قرص الحاوية.
  • نشر /.well-known/assetlinks.json وapple-app-site-association على نفس الدومين.

C3 دين تقني: إعادة كتابة localhost → 10.0.2.2 تنظيف

الدليل
lib/utils/formatters.dart وitem_marker_widget.dart يستبدلان localhost بعنوان المحاكي.
الأثر
حيلة مقترنة بالمحاكي. مع دومين حقيقي تصبح بلا أثر، لكن يُستحسن حذفها وضمان أن الخادم يُرجع روابط وسائط مطلقة صحيحة (عبر build_absolute_uri بالدومين العام).

الدليل

✓ خامسًا: الخادم (Django) — ناضج، يحتاج بيئة إنتاج فقط

الإعداد الأمني من الأفضل الذي رأيته في مشروع بهذا الحجم: يُبنى ليفشل بأمان، لا يكشف الأسرار، ومحمي على مستوى لوحة الإدارة.

نقاط قوة مؤكّدة من الكود جيّد

  • الأسرار محمية: .env وfirebase-credentials.json و*.key/*.pem ضمن .gitignore، ولا شيء منها مُتتبَّع في git.
  • DEBUG يفشل مغلقًا: غياب المتغيّر ⇐ False. ويرفض التشغيل لو بقي SECRET_KEY الافتراضي أو * في ALLOWED_HOSTS عند الإنتاج.
  • ترويسات الأمان خلف !DEBUG: إعادة توجيه SSL، كوكيز آمنة، HSTS سنة كاملة مع preload، X-Frame DENY، nosniff.
  • لوحة إدارة محصّنة: مسار مخصّص (ADMIN_URL_PATH)، django-axes (قفل بعد 5 محاولات)، مصادقة ثنائية (django-two-factor-auth)، auditlog، ratelimit، Sentry.
  • بنية حديثة: DRF + SimpleJWT + Channels(WebSocket) + Celery + Redis + Firebase Admin + رموز Agora على الخادم.

ما يجب ضبطه قبل الإنتاج إعداد بيئة

  • بيانات قاعدة البيانات الافتراضية: يوجد fallback إلى root/'1234' في settings.py — تأكّد أن متغيّرات البيئة الحقيقية مضبوطة في الإنتاج (المستخدم/كلمة السر لا يعتمدان على الافتراضي).
  • ملف اعتماد Firebase: وفّره بأمان على الخادم (متغيّر مسار/سرّ مُدار)، لا داخل الصورة/المستودع.
  • النسخ الاحتياطي والمراقبة: Sentry موجود ✓ — أضِف نسخًا احتياطية دورية لقاعدة البيانات وملفات الوسائط، وتنبيهات صحّة.
  • WebSocket خلف Nginx: اضبط ترقية الاتصال (Upgrade/Connection) لتمرير wss://.
